## 修复：符号链接音乐文件漏扫

根因：`MusicScannerService.collectCandidates` 用不带 `FileVisitOption.FOLLOW_LINKS` 的 `Files.walk`，
不下降进入符号链接目录。三类场景漏扫：① `musicPaths` 路径本身是目录符号链接（如 `~/Music -> /mnt/data`，
一首都扫不到）；② 库目录内嵌套的目录符号链接（其内容全部丢失）；③ 指向单个文件的符号链接
（此场景原 `isRegularFile` 跟随链接，其实能收录）。

修法：改用 `Files.walkFileTree(path, EnumSet.of(FOLLOW_LINKS), MAX_VALUE, visitor)`，
`visitFile` 里用「跟随链接读取的 attrs.isRegularFile()」判断并过滤扩展名；`visitFileFailed` 里
对 `FileSystemLoopException` 就地 `CONTINUE`（只跳过该子树、不中断整次扫描），对断链/权限不足静默跳过。
关键点：循环链接若不处理会让 `Files.walk` 抛 UncheckedIOException 拖垮整个库目录，`walkFileTree`
+ `visitFileFailed` 才能既跟随链接又安全跳过循环（已用 /tmp 探测脚本验证三态）。

新增 4 项测试（MusicScannerServiceTest）：目录链接、文件链接、库路径本身为链接、循环链接不中断。
全量 115/115 通过（0 失败 0 中止）。README 同步更新「自动扫描/`musicPaths`/扫描不到文件 FAQ/测试覆盖表」。

## 文档勘误：两处 README 与代码不符

1. **架构图淡化 HTTP /control 风险**：`HttpGateway.handleControl` 无鉴权直接 `dispatch`

2. **progress 附 serverTime 描述错误**：`ProgressMapper.buildProgress` 从不写 serverTime，
只有 `PlaybackEngine.buildStartedSnapshot`（start/playSongById 用）才写。README 原 338 行声称
「status=playing 时附 serverTime」，与代码及示例响应（无 serverTime）双重矛盾。修法：对齐代码——
progress 不含 serverTime，serverTime 仅在 start/select 的 started 快照返回；并顺带修正 progress

## 修复：三处并发竞态（代码审查）

1. **UnixSocketServer 的 socket 文件删除竞争**：原 `cleanupSocketPath()` 在 `start()` 的
`finally` 里异步执行（accept 线程），`stop()` 返回后旧实例迟到的删除可能误删新实例刚 bind 的
socket 文件。修法：把删除移到 `stop()`（关闭 channel 之后同步完成），`finally` 只保留
`connectionPool.shutdown()`。新增 `UnixSocketServerTest`（stop 同步删文件 + 重启重 bind）。

2. **PlaybackEngine.advanceAndCommit 校验后重查窄竞态**：原实现先 `advanceToNextValid(this::exists)`
（校验）、再 `getMusicById`（重查），两次查询之间并发重扫移出该曲时返回 null 却已推进游标到幽灵项。
修法：`PlaybackSession` 新增泛型 `advanceToNextResolved/advanceToPreviousResolved(Function<String,T>)`，
把校验与解析合二为一（每个候选只查一次、命中即返回解析对象）；`advanceToNextValid(Predicate)` 与
`getNextSong/getPreviousSong` 改为委托该泛型方法；引擎改用 `this::resolve` 返回 MusicFile，彻底消除
二次查询。新增 FlappingScanner（查到即移出）两个用例 next/previous。

3. **SessionRegistry.startSession 懒重建的 ID 冲突窗口**：`connect` 的「分配 + put」与
`disconnect`/`inspectSessions` 的「remove + 放回空闲池」原本都拆成锁内锁外两步，窗口内 `startSession`
会把「0 号不在 map」误判为空闲而懒重建 legacy，与即将写入/释放的 0 号叠加成「双重占用」，导致下个
连接二次分配 0 号。修法：新增 `registerSession`（分配+构造+put 整体持锁）与 `removeSession`
（remove+放回空闲池整体持锁），删除 `releaseSessionId`。新增并发压力 + 反射校验「空闲池 ∩ 占用 map = ∅」。

全量 120/120 通过（0 失败 0 中止，115 + 新增 5）。沙箱内 Maven 读 .m2 元数据仍被 Security Center
拦截，沿用「手动 javac + JUnit Launcher」验证。

## 死代码清理：删除服务端播放时钟

背景：CLI 客户端已移除，`PlaybackSession` 的权威时钟字段（segmentStartEpoch/positionBaseMillis/
playing/prepared/preparedSongId/lastClientSyncEpochMillis）及其方法（startOrResumePlayback/
beginAuthoritativeClock/prepareForPlayback/pausePlayback/seekPlayback/onSongChanged/stopIfEnded/
getPositionMillis/getSegmentStartEpoch/markClientSynced 等）无任何消费者，属「生产者还在、消费者已走」
的内部自循环。位置归客户端（浏览器 audio.currentTime）。

删除范围：
- `PlaybackSession`：删时钟字段与方法，只留 playlist/currentIndex/playMode/shuffleHistory/rng/
  durationMillis（durationMillis 仅作元数据展示）；类注释新增「刻意不持有时钟」说明。
- `ProgressMapper`：只返回 songId/title/artist/album/duration/playMode，status 恒为 "unknown"
  （有歌）/"empty"（空），删除 position/percent/isPlaying/ended/lastSyncedAt/syncDueAt。
- `SessionRegistry.inspectSessions`：删 stopIfEnded、心跳超时 pausePlayback、客户端同步对账检查项 2
  及 CLIENT_SYNC_INTERVAL_MS；只留「心跳超时记 stale 日志 + SESSION_DELETE_AFTER_MS 删除会话」。
- `ClientSession`：删 lastSyncWarnEpoch/markSyncWarned/getLastSyncWarnEpoch。
- `PlaybackEngine`：删 start()/buildStartedSnapshot/markClientSynced；applyPlay 不再调
  startOrResumePlayback（改为 setDurationSeconds 记元数据时长）；prepare 删 prepareForPlayback 与
  isPreparing；playSongById 删 prepareAndStart/markClientSynced（改 syncDuration + buildProgress）；
  getProgress 删 stopIfEnded；pause/seek 不再改服务器状态。
- `CommandDispatcher`：删 case "start" 与 case "sync.ack"。
- `PlaybackService`：删 start()/markClientSynced() 转发。
- 测试：删 PlaybackSessionTest 13 条时钟用例 + PlaybackServiceTest 2 条两段式握手用例；新增负向守护
  `progressDoesNotExposePositionOrServerClockFields`；SessionManagementTest 三处 start/isPlaying 用例
  改为「stale 不删除 / 3min 删除 / legacy 不治理」。
- README：删「播放进度时钟/两段式播放握手/客户端同步对账」三节与 start/sync.ack 命令、修正 progress
  示例、设计约定新增「播放位置归客户端」一条、心跳「先暂停」改「记 stale」。
